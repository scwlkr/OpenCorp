# Company power controls

Use `opencorp full`, `opencorp low`, or `opencorp stop` locally. In the configured private Telegram bot chat, send exactly `/full`, `/low`, or `/stop`. Only the verified Owner sender and chat can control execution. Commands take effect through the shared service without a model turn. The web controls and terminal (`f` Full power, `l` Low power, `s` Stop) use the same state. Terminal refresh is `x`.

Full power uses existing configured, qualified inference capacity and resource admission. Low power limits dispatch to one turn at a time and local models with a known installed size no greater than 2 GB, using 16K context. These are conservative resource limits, not claims of model competence. Only the employee's already selected model and configured alternatives are considered. Suitable permitted hosted work remains eligible; confidential work stays local. Larger or unavailable work remains queued with a resource-wait reason. Low power discovers installed models without downloading a default model. It does not alter employee identity, model selection, permissions, provider eligibility or spending policy.

Changing power mode interrupts active company turns, retains progress and stops owned runtimes to release loaded models before restarting under the selected mode. Stop persists before cancellation, revokes active worker authority and prevents new execution. It cannot undo an external request already dispatched. Existing runtime/effect recovery holds uncertain actions for reconciliation before any retry. These controls do not retire products, stop external hosting or cancel independently hosted services.

The selected power mode and lifecycle survive daemon restart. A stopped company stays stopped; use Full power or Low power for deliberate resume. Legacy `start`, `resume` and `pause` remain available; start/resume retain the selected mode. Existing companies without a stored mode retain Full power behavior. Sleep suspends local execution; on wake/restart retained assignments and run/effect recovery remain authoritative. No claim is made that a remote request can be cancelled after dispatch.

Telegram keeps accepting commands while stopped. Only the direct control receipt can be sent while stopped; ordinary replies wait. Control intake, applied disposition and outgoing receipt are persisted and deduplicated. A failed or interrupted cleanup is reported as unconfirmed; failed Full/Low transitions hold execution paused for inspection and deliberate resume. Uncertain Telegram receipt sends use the existing reconciliation procedure, never a blind resend. Older messages from before power-control activation are not retroactively interpreted as controls.

Inspect `opencorp status --json` for `company.state`, `company.powerMode`, resource limits, queued work and actual runtime processes. A stored mode alone is not proof of resource release: inspect active runs, owned processes and actual subsequent work. Full power does not force work to exist or bypass memory/provider admission.

# Company state and corporate commands

`src/storage/store.ts` exports `CompanyStore(dataRoot)`. `src/core/types.ts` exports the records shared by API, WebUI, CLI and TUI. The supervisor is the only SQLite writer; worker tools use `command(actor, command)` after the broker derives identity from its scoped token and bound runtime session.

The store opens `company.sqlite`, applies explicit migrations, enables WAL and a busy timeout, and retains indexed operational identities/status relationships in SQLite. Flexible record fields are JSON; generated indexed columns keep run/assignment/employee status queryable. `put`, `update`, `get`, `need` and `list` are **trusted supervisor integration methods**, never worker API capabilities. Never hold these transactions across a network or model call.

## Identity and authority

`bootstrap()` creates one company, three Elders, one CEO, policy and the three registered products in one transaction. Running bootstrap again preserves their UUIDs, appointments, names and lifecycle. It initializes narrative profiles and source-linked mandate knowledge. The supervisor schedules the CEO's first real local-model assignment; bootstrap does not invent product assessments, projects or strategy.

An employee references a position and a local model independently. Position changes close the former appointment and create a historical appointment while preserving employee identity, role versions and experience. Nonexecutive staff have a home manager. Assignments separately have a project supervisor and home-management acceptance. A borrowed assignment waits until its home management accepts it.

Worker actors have `{kind:'employee', employeeId, runId, policyRevision}`. The store checks active employment, run identity, active run status, token revocation, current policy and running lifecycle. The broker additionally authenticates the runtime session. Imported role text and Markdown do not participate in authorization.

CEO proposes executive positions and candidates. Executive appointment/replacement/dismissal decisions receive one immutable initial vote from each of the three current Elders. `snapshot(actor)` hides peer votes and governance events until that actor has voted. All three initial judgments are collected before applying a two-of-three result, retaining dissent. Owner may override an executable decision or replace an Elder. Company commands cannot eliminate or transfer Elder seats. Executive replacement transfers current management responsibilities to the replacement and retains the former employee's unfinished work for explicit reassignment.

Appointment decisions include a derived `appointmentEffect` in actor-filtered snapshots, bounded summaries, full detail reads and the WebUI decision card. It mirrors the execution branch: no `payload.employeeId` means a new employee identity, even with an existing display name; an explicit ID selects that existing employee. The preview identifies same-name employees by badge, ID and current position and states which remain unchanged (or occupy a replacement target). It does not allocate a future UUID, infer identity from names, validate approval merits, or rewrite stored proposals and votes. Normal appointment validation and independent judgments still apply.

Ordinary corporate commands:

- Product: `product.assess`, `product.goal`.
- Organization: `department.create`, `position.create`, `employee.hire`, `employee.appoint`, `employee.reassign`, `employee.model`, `employee.dismiss`.
- Projects/work: `project.create`, `project.update`, `assignment.create`, `assignment.accept`, `assignment.update`.
- Governance: `decision.create`, `decision.vote`; Owner-only `decision.override`, `elder.replace`.
- Results/learning: `artifact.record`, `review.record`, `message.send`, `knowledge.write`, `role.update`, `experience.record`.
- Owner: `control`, `policy.update`, `attention.resolve`, `action.approveCost`.

Elders should use the typed MCP `vote_decision` tool with direct required fields `decisionId`, boolean `approve`, and independent `rationale`. It calls the same `decision.vote` domain command and returns a bounded receipt; identity, assignment matching before the initial vote, immutability and blind peer visibility are unchanged. The generic `company_command` route remains available. Missing fields or malformed votes never acquire inferred judgments or reasons.

Management can use typed `create_assignment` with direct employee, project, instructions and acceptance fields; normal supervision and shared staffing acceptance still apply. During an active trusted fault diagnosis, `record_blocked_diagnosis` derives the exact latest failed run and original assignment, then atomically records a new precise blocked reason, linked strategy disposition and both current-run command receipts. It preserves the original acceptance and blocked status. A duplicate unchanged reason is rejected. Creating actionable subset work is a separate leadership decision through `create_assignment`; final prose does not complete the diagnosis.

New review assignments require an independent employee, explicit `projectId`, and `payload.artifactId` identifying an existing artifact in that same project. Retrieve the artifact through `company_detail {collection:'artifacts',id,view:'record'}` first. Its original assignment must agree with the project; company-maintenance projects remain supported. Project management authority and home-management staffing acceptance both apply. `assignment.update` rejects `projectId` and `payload` fields instead of silently ignoring or rebinding scope. Authorized management may cancel incorrect work with a reason and create a correctly scoped assignment; existing records and acceptance are preserved.

The same scope check runs before queued review dispatch, including direct `claimNext`. Inactive invalid legacy reviews become blocked with their exact discrepancy and prior status/reason retained in `reviewScopeHistory`; active runs and historical verdicts are untouched. One durable `review-scope:<assignmentId>` company-workspace correction goes to existing management with authority over the old supervisor and artifact project and access to the retained evidence. It must record a current-run explained cancellation or new precise blocked disposition of the invalid review; replacement work requires ordinary correctly scoped creation and independent staffing. Scope is never rebound or automatically retried. Unavailable authorized management is recorded explicitly, and generic queued model-failure diagnoses are superseded by this scope correction.

Assignment dependencies are completion prerequisites; `payload.sourceAssignmentId` records provenance without holding dispatch. Supervising management can explicitly replace dependencies on queued, blocked or needs_changes work with a rationale. Audited edges retain actor/run, prior and resulting state; self/transitive cycles, unknown IDs and active/closed-work edits are rejected. Queued work held by blocked, cancelled or missing prerequisites receives a durable supervisor diagnosis. Completion requires its actual audited correction or a precise explicit blocked/cancelled disposition; original acceptance and genuine prerequisites are preserved.

Corporate tool schemas give each command its own required-field branch and explicitly name all supported command fields, goal properties, review/governance metadata and permitted browser arguments. The pinned Ollama tool representation drops `additionalProperties`, so schema openness alone does not advertise nested fields to the local model. Missing required command fields return a concrete corrective shape before mutation; domain authority and state checks remain authoritative. Arbitrary retained strategy metadata still passes through the backend, while named operational fields are visible in the model's tool schema.

Worker `company_command` requires an explicit allowed `command.type`; governance kinds such as `executive.appoint` belong inside `decision.create`. Missing or unknown types return an actionable error without inferring a mutation. Successful worker replies are bounded receipts: ordinary IDs, statuses, booleans and small operational fields keep their types; large values identify their excerpts, and product repository bindings are explicitly omitted. Full records remain unchanged in storage and receipts provide scoped `company_detail` pointers. Initial vote receipts retain the vote ID, decision ID and actual boolean judgment. The bounded `votes` collection and vote detail reads use the same actor-filtered snapshot: an Elder can read peer judgments only after recording their own initial vote on that decision. The active CEO can also read finalized votes after all three eligible Elders have recorded initial judgments and the decision has closed; uninvolved workers cannot.

A rejected executive appointment schedules one durable CEO correction assignment per decision, with exact retained decision and vote IDs. Completion requires a current-run revised appointment proposal or explicit strategy withdrawal linked by `payload.rejectedDecisionId` and `payload.reviewedVoteIds`; final prose and unrelated updates cannot satisfy it. Executive startup requires two registered product projects with actionable active staffing or independently reviewed completed outcomes. Parked, blocked and company-only placeholders cannot count as ready product work.

Code artifacts and reviews are broker-mediated: the public worker `company_command` must reject direct `artifact.record`/`review.record` calls in favor of commit/verify/review tools with observed provenance. Code review approval requires an independent employee and run, an explicit tracked review assignment bound to artifact ID, the latest exact artifact identity, and trusted `artifact.verification = {identity, passed:true, receiptId, ...}`. The broker must verify actual clean workspace head, canonical verifier receipts and reviewer inspection. A final sentence does not complete implementation work.

Artifact approval means readiness, not completion of its originating implementation assignment. Supervising management declares `assignment.update {assignmentId,completionRequirements:[{criterion,source:'artifact'|'delivery'|'release',authorship?:'external',version?:exact release version}],rationale}`; creation accepts the same requirements and rationale. Every criterion must exactly match the unchanged original acceptance. There is no inferred/default evidence kind. Declarations are audited once and cannot be changed or downgraded; review runs cannot declare them. `external` requires retained imported-PR authorship and cannot be satisfied by employee-authored maintenance. Leadership chooses these requirements from the actual task; the backend does not classify prose with regular expressions.

An independent reviewer may retain `review_work.assignmentAcceptance:[{assignmentId?,criterion,evidence,source,authorship?,version?}]` matching the declared requirements, under the same complete inspection and canonical guards. The target defaults to the artifact's original assignment; a separate artifact may also cover its explicit same-project `payload.sourceAssignmentId` parent. Future delivery/release coverage is conditional until observed receipts exist. Supplemental coverage uses a new review assignment and works for approved but incomplete or explicitly blocked original work. Supervising management then uses `assignment.update {assignmentId,status:'completed',completionEvidence:[{criterion,rationale,sources:[{type,id}]}],rationale}`. Every original criterion requires matching independent coverage and exact artifact, confirmed merge/default ancestry, or published exact-version receipts. Owner uses the same evidence gate. Dependencies and project completion require validated assignment completion; artifact readiness still permits authorized delivery independently.

Scheduler reconciliation audits legacy implementation completions without this proof back to `awaiting_review`. It preserves prior status, completedAt and evidence in `completionHistory`, records `completionReconciledAt`/`completionPending`, and emits `assignment.completion_reconciled`; it never rewrites original acceptance, artifacts or old reviews. A deduplicated company-workspace supervisor followup declares missing requirements, confirms actual completion, requests correctly scoped independent coverage, or retains an explained block/cancellation. It cannot complete through unrelated commands or prose, and does not retry product effects. Valid existing evidence completions remain unchanged.

Project completion is separate from an artifact approval, merge or release. `review_work` may supply optional `projectAcceptance:[{criterion,evidence,source:'artifact'|'delivery'|'release',version?}]`: criterion must exactly match current project acceptance; evidence is the independent reviewer's explanation; release coverage requires the exact expected version. Partial artifacts may satisfy their narrower declared assignments with no or partial project coverage. Artifact coverage concerns the actual reviewed output; delivery/release coverage depends on a subsequent observed provider outcome, not a promise that it happened. An already approved artifact can receive missing coverage through a new independent review assignment with `payload.artifactId`, using `review_work {artifactId,verdict:'approved',rationale,supplementalAcceptance:true,projectAcceptance:[...]}` after actual exact-artifact inspection. This appends evidence and completes only the new review assignment; original completion/history remain unchanged. Unmet criteria require actual further work rather than fabricated coverage.

Leadership records `project.update {projectId,rationale,completionEvidence:[{criterion,rationale,sources:[{type:'artifact'|'delivery'|'release',id}]}]}`. Artifact/delivery IDs identify the reviewed source artifact; release IDs identify the published package. Each source must belong to the same project and match an independent exact-artifact review's explicit criterion/source mapping. Code needs passing canonical receipts; delivery needs a retained confirmed merge/default-branch ancestry receipt; release needs the reviewed version, package checks and observed publication receipt. Stored sources add validated `reviewId`, `identity` and available provider references. Partial evidence keeps the project active. `status:'completed'` additionally requires every current criterion and terminal project assignments. Changed acceptance clears obsolete evidence, retains acceptance/completion history, and reopens a formerly completed project. No routine Owner approval is introduced.

`inspect_artifact` returns bounded diff pages with `offset`, `nextOffset`, `totalCharacters`, `contentIdentity`, `inspectionComplete` and `nextUninspectedOffset`. Persistent interval coverage is bound to the employee run, artifact, exact base/head and SHA-256 of complete captured content. Repeated or out-of-order pages cannot conceal gaps; `review_work` rejects incomplete or changed inspection. Ordinary small diffs finish in one call. Complete Git diffs over 2 MB and narrative artifacts over 200 KB are refused before recording a page. Artifact metadata excerpts link to `company_detail` with `view:"record"` for complete paged canonical commands, checks and receipt/log paths; ordinary content reads never count as review inspection.

Broker process logs may retain a tail but report stdout/stderr truncation and observed character counts. `checked` rejects truncated stdout, including oversized workflow inputs used by cost qualification. Full source/diff capture has an explicit size limit and never treats a log tail as complete evidence.

Authorized artifact readers can retrieve retained canonical, dependency-preparation and verification-boundary output through `company_detail {collection:'artifacts',id,view:'verification'}`. Follow its exact `nextCall`, including the current `receiptId`, for each 8,000-character page. The broker derives the protected log path, validates matching artifact/check/run receipts, rejects symlinks, changed evidence and active replacement, and redacts the complete text before paging. New receipts bind the stored bytes and SHA-256. Older receipts remain unchanged and are explicitly labeled `legacy-file-time`: their weaker binding uses the fixed path, matching checks/run and millisecond file modification time. Missing or unprovable legacy output, non-text files and files over 2 MB are refused. These reads never grant independent artifact-inspection credit or passing verification.

## Scheduling and external effects

`claimNext({workspace?,leaseMs?,assignmentId?})` atomically changes a ready assignment to running and creates an Employee Run. Claims respect the persisted lifecycle, dependencies, home-management acceptance, employee status and inference limit. The default is one inference slot; enabling two requires a retained realistic large-plus-small qualification. Large models stay mutually exclusive; qualified small profiles carry `sizeClass:'small'`.

Every scheduled company employee run uses the locally supported 32,768-token context budget. Actual governance input exceeded the 16K compaction threshold before leaving sufficient output allowance; bounded tools and state excerpts still apply. This changes neither model assignment nor inference concurrency.

The persistent employee system prompt keeps a compact assignment anchor: exact assignment ID, kind, project when present, and the assigned review artifact ID. After native compaction loses task context, the employee retrieves the original instructions, acceptance and retained progress through scoped `company_detail` pages. Review anchors retain the independent inspection and `review_work` verdict obligation, with the original acceptance retrieved through the artifact record. Full task text, arbitrary payload and company state are not duplicated into the anchor. Conversation replies retain their existing final-response deliverable; other checkpoint and authority checks remain unchanged.

Use `bindSession(runId,sessionId,workspace?)`, `heartbeat(runId,leaseMs)`, `revokeRun(runId,reason)`, and `finishRun(runId,{status,text,error,transient,...})`. Runs retain attempts, workspace, model, session, lease, revocation, result and corporate commands. One transient retry is allowed. Code output without an artifact blocks for management inspection. Management completion requires persisted commands or a trusted measurable `managementResult.summary`; the scheduler separately checks meaningful execution before declaring success.

A native agent iteration-limit marker does not invalidate a persisted checkpoint. When the checkpoint is missing, the scheduler retains the full runtime result and native-limit evidence, classifies `step_budget_exhausted`, and blocks for the existing supervisor diagnosis instead of automatically starting another correction run. Ordinary incomplete checkpoints without a budget failure may receive at most the configured `policy.maxCorrections` automatic corrections. Prior failed runs and preserved files remain intact.

When the final text exactly echoes the pinned native step-limit protocol and the run records that limit, it is not published as employee discussion or learning. Existing exact run-linked copies are omitted from those projections; raw records, native history, run output and checkpoint events remain unchanged. Genuine employee summaries and quoted protocol text remain visible.

Transient classification reads the known OpenCode API-error status and retryability fields, or explicit transport error codes/messages through at most four causes. A permanent provider response or `isRetryable:false` is not retried because its headers, URL or body mention a timeout. Typed runtime budget exhaustion remains nontransient. Eligible transport/temporary-provider failures still receive only the configured single retry; complete error evidence remains retained.

The latest failed run of genuinely blocked work creates one durable `fault:<runId>` diagnosis for its supervisor, including self-supervised CEO/Elder work. Reconciliation covers a crash between failure recording and scheduling. Diagnosis tasks never recursively create diagnosis tasks, and a recorded governance vote remains complete despite a later response failure. Only the exact trusted diagnosis may change its own CEO/Elder's installed local model while the original work is blocked; normal personnel authority is unchanged. A newer attempt or a completed/cancelled original assignment invalidates the old diagnosis, and stale correction writes are denied without changing retained history. Completion requires a current-run model/instruction correction and recorded retry of that exact assignment, or a changed blocked reason plus a current-run strategy decision linking both failed IDs. Unchanged retries fail before requeue; prose and unrelated writes cannot complete diagnosis. Failed-run evidence, retry decisions and correction provenance remain retained. Peer governance diagnosis records and model-change reasons stay hidden until the reader's independent initial vote. That origin follows child governance assignments and subsequent decisions; a peer receives child voting work only after its prerequisite initial judgment. Early runtime errors retain their actual typed evidence without fabricating absent session/message files.

`recoverRuns(observe)` requires the supervisor to observe tracked runtime ownership and workspace state. Confirmed absent runtimes preserve files and requeue interrupted assignments. Unknown ownership becomes uncertain and blocks only that work. Prepared/dispatched external effects never acquire a retry merely because a process restarted.

`prepareAction(actor,input)` persists sender/run/product, destination, intended content, unique deduplication key and cost evidence before any side effect. Unknown costs or positive costs block with an exact spending request. `action.approveCost` accepts only an Owner-approved concrete action and amount; it does not change the $0 unapproved allowance.

`dispatchAction(actor,id)` rechecks identity, lifecycle, policy, cost approval and review/check/head requirements for delivery. Only a prepared intent dispatches. `resolveAction(id,{status,remoteRef,result})` records observed results; success requires the actual remote reference. `reconcileAction(id,{state,evidence,remoteRef})` accepts provider observation, never an optimistic model statement. A confirmed absent effect allows at most one retry. Unknown effects remain uncertain. Already-dispatched results may be recorded after pause; no new worker effect may begin then.

## Knowledge, backup and restore

Markdown is stored beneath `vault/company`, `products`, `departments`, `projects` and `employees/<UUID>`. Generated operational mirrors and editable narrative are separate. File changes refresh FTS5 with source/author/hash/version provenance. Generated mirror edits are preserved with an attention conflict; SQLite authority does not change. Knowledge corrections may identify `supersedes`. Prior written versions live in `vault-history`.

`readKnowledge(id)` returns metadata plus content. `searchKnowledge(query,{scopeId?,limit?})` safely quotes FTS terms. `vault.retrieve({query?,scopeIds?,budgetChars?})` selects relevant records inside a bounded context budget; references retain paths and provenance. Vault paths reject traversal and external symbolic links.

`backup()` synchronously creates a consistent `VACUUM INTO` SQLite snapshot and matching vault/history copy in one writer event-loop turn, then writes a hashed manifest. `restore(path)` requires paused/stopped state, validates the manifest and database integrity, restores identity/knowledge, increments policy revision and leaves the company paused. Credentials are not restored. Runs are revoked, interrupted work needs inspection, historical pending actions become uncertain, and observed sends newer than the snapshot are retained by deduplication key. Restore cannot erase a send receipt and thereby cause replay.

# Verification and acceptance

`mise exec node@24.20.0 -- npm run verify` checks types, lint, domain/integration tests and production build. Controlled failure fixtures test authorization, state transitions, uncertainty and restoration; they are not autonomous product evidence.

`mise exec node@24.20.0 -- npm run verify:local-runtime` runs the actual pinned OpenCode against private local Ollama profiles. It requires genuine code/tool output, independent alternative-model review, image understanding and cancellation. It uses a disposable workspace, not a portfolio product.

`mise exec node@24.20.0 -- npm run verify:corporate-runtime` exercises the full corporate MCP catalog through actual local Nemotron and OpenCode (use `-- --model qwen-main` to qualify Qwen instead) against a disposable company. It checks real domain mutations and run receipts for model changes, assignments and linked blocked diagnoses, including nested command payload fields. Its synthetic company records cannot count as portfolio work.

`mise exec node@24.20.0 -- npm run verify:acceptance` exercises the installed company journey and checks actual persisted employee/artifact/review/delivery records. It must fail while any required acceptance outcome is missing. The builder may diagnose/fix OpenCorp, but must not hand-author product code and attribute it to employees.

Release acceptance requires a real portfolio improvement from OpenCorp employee runs, independent review and canonical repository checks at the delivered commit, a second project checkpoint, durable recovery/control and $0 denials, shared live interfaces, installation, and backup/restore. The final record links actual company artifacts and GitHub outcomes. Ongoing autonomous work is distinct from proven long-term strategic competence.

A later failed or interrupted author turn does not erase a completed employee commit. The first-delivery verifier retains that failed/interrupted status and requires the exact native `commit_work` result, broker artifact command, employee/assignment/session/model binding, and immutable product base/head. Such a commit qualifies only after a later successful local run performs canonical verification of the same head, followed by the separately required independent review and observed merge. Other run-success requirements remain unchanged. A record or commit created by the builder, an imported candidate, prose, or copied tool evidence cannot replace those receipts.

The first delivery must remain employee-authored; imported PR code cannot satisfy it. The second project may instead show company-performed executable progress on an external PR: its immutable selected candidate, actual local import/verification runs, passing canonical receipt and log, and a separate employee's complete exact-diff review with explicit current project-criterion evidence. Criterion mappings describe review scope, including conditional future delivery/release coverage; they do not establish completed criteria. Acceptance rechecks the live PR identity and clean candidate workspace. Import alone, copied checks, mismatched runtime evidence, or a review of another head cannot pass. This narrow second-project route preserves external authorship and makes no merge or project-completion claim; the existing employee-authored narrative/commit checkpoint route remains available.
